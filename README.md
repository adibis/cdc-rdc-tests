An emerging tool-neutral conformance suite for clock-domain crossing (CDC) and
reset-domain crossing (RDC) checkers. Each case is a small SystemVerilog design
with the exact findings a correct checker reports, so any checker, open or
commercial, can measure recall and precision against fixed ground truth instead
of against another tool's output. It is analogous in purpose to
[sv-tests](https://github.com/chipsalliance/sv-tests), but CDC and RDC have no
language standard to test against, so the suite states its own contract: what
category each rule belongs to (safety, protocol, policy, constraint or record),
and the clock, reset, startup and traffic assumptions every verdict holds
under.

**Status, 0.1.** One reference checker passes every case. That shows the
oracles are consistent with one implementation, not that they are neutral, and
no independent checker has been scored yet. Reproducible results from other
checkers, disagreements included, are the most useful contribution: a
disagreement is evidence about the oracle or about the checker, and either is
worth having.

## What is in it

<!-- stats:begin (generated by scripts/gen-catalog.py; do not edit) -->
Tier 1 holds 213 cases covering 36 rules (CDC-026 only records notes), with 220 expected findings: 176 violations (errors and warnings) and 44 notes. 151 cases have a nonempty oracle:

- **141 violation cases** expect at least one error or warning at a given location, and may also expect notes.
- **10 note-only cases** expect informational records and nothing else; under `--ignore-notes` they must be silent.

The other 62 are **silence cases**: they plant the approved pattern (a two-flop synchronizer, a gray-coded bus, a locally synchronized reset) and must report nothing.

By [category](docs/rule-map.md#categories), the violations split 113 safety, 38 protocol, 9 policy, 16 constraint. 16 cases rest on a designer's promise, a [waiver attribute](docs/attributes.md) the checker takes at face value.
<!-- stats:end -->

Silence is a verdict: a checker that reports everything fails.

- **Tier 1**: one scenario per case, exact expected findings. Shipped.
- **Tier 2**: OpenTitan crossings its designers waived, traced to endpoints.
  Planned.
- **Tier 3**: clean production modules that must stay quiet. Planned.

Every case is real, synthesizable SystemVerilog. CI compiles each one with
[Verilator](https://github.com/verilator/verilator),
[Xezim](https://github.com/aionhw/xezim) and
[slang](https://github.com/MikePopoloski/slang), and synthesizes it with
[Yosys](https://github.com/YosysHQ/yosys) through both its own front end and
[yosys-slang](https://github.com/povik/yosys-slang). None of these checks
crossings, and synthesis must also find no multiple drivers, undriven nets or
combinational loops. So when a checker fails a case, the reason is the
crossing, never the syntax or the netlist.

Where a verdict rests on what the hardware does, it is backed by a bounded
formal check in SymbiYosys. Three harnesses cover three claims: event loss
across a toggle synchronizer (every CDC-013 case, at its SDC clock ratio), gray
order across a crossing (every case that rests on gray coding), and runt-free
clock switching (the clock-mux cases). A bug verdict needs a counterexample:
a CDC-013 bug case must drop an event under an unconstrained stream, and keep
every event when they are spaced out. A quiet verdict means no counterexample
within the harness depth, not an unbounded proof. Every run must also reach a
cover, so a check that never exercises the design cannot pass. Each harness
fixes its reset, warm-up, clocks, traffic and depth;
[docs/assumptions.md](docs/assumptions.md) lists them. See `formal/`.

## How a case is scored

A case passes on an exact match. Each expected finding pairs with one reported
finding by rule id and location (a source line, or the destination name for a
port). Nothing may be left over unless the case says extra findings are
allowed. Rule ids are the suite's own numbering; [docs/rule-map.md](docs/rule-map.md)
defines each one, so another checker can map its rules onto them.
[docs/method.md](docs/method.md) has the full contract.

## Run it

The bundled runner drives [icarium](https://github.com/adibis/icarium):

```sh
python3 run.py --icarium-bin /path/to/icarium [--tier 1] [--case ID] [--ignore-notes]
```

It needs `yosys` on `PATH` (tested with 0.70) and Python 3, standard library
only. It exits 0 when every case matches. `--ignore-notes` drops
informational findings on both sides, for checkers that report violations
only.

To run another checker, give it each case's `design.sv`, `design.sdc` and
`top`, and compare its findings with `manifest.json` as
[docs/method.md](docs/method.md) describes. A runner for your tool is a welcome
contribution.

CI runs icarium as a reference checker at the commit in
`.github/icarium-commit`. Its verdicts are not the ground truth; the
manifests are, and a case that icarium gets wrong stays as written.

A score counts every case: a case a checker cannot run, or runs outside its
supported scope, counts against it. To add a row, open a pull request with the
checker, its version, its rule mapping and supported scope, the command you
ran, and the per-case results file; [docs/method.md](docs/method.md#writing-a-runner)
says what each must contain.

## Layout

- `cases/tierN/<id>/`: `design.sv`, `design.sdc`, `manifest.json`
- `docs/catalog.md`: every case by rule (generated by `scripts/gen-catalog.py`,
  which also writes the case counts above)
- `docs/method.md`: how verdicts read and how to run another checker
- `docs/rule-map.md`: the suite's rule numbering, with contracts and categories
- `docs/rules.json`: each rule's category, machine-readable
- `docs/locators.md`: which endpoint each rule reports on
- `docs/attributes.md`: waiver-attribute spellings and meanings
- `docs/sdc-subset.md`: the five SDC commands cases use
- `docs/assumptions.md`: the reset, startup and traffic every verdict assumes
- `schema/manifest.json`: the manifest schema
- `run.py`: elaborate, check, compare with the manifest; `--results` writes
  the per-case results file
- `scripts/compile-check.py`: compile or synthesize every case with one tool
- `formal/`, `scripts/formal-check.py`: bounded formal checks behind behavioral verdicts

## Where the cases come from

- `cdc*`, `rdc*`: written from the rule contracts, one bug or one silence
  proof each.
- `fx_*`: drawn from icarium's rule fixtures, with verdicts reviewed against
  the rule contracts.
- `e2e_*`, `scan_design`: drawn from icarium's end-to-end and suppression
  suites, where the verdict does not depend on the tool.

A manifest records the findings its author intends, and the runner compares a
checker with that manifest, never with an earlier run of the same checker.
Cases whose verdict depends on one tool's modeling choices (gate-structure
lint, memory opacity, reset-port policy) stay out: what this suite asserts,
any correct checker should agree with.
